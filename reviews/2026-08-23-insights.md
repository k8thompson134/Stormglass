# QA Review — Insights (feature mode)

Scope: `frontend/src/components/Insights.tsx`, `frontend/src/utils/symptomAnalysis.ts`,
`frontend/src/utils/symptomAnalysis.test.ts`, `frontend/src/components/TrendsModal.tsx`, and
the `current`/`error` prop wiring in `App.tsx`. This is the feature reworked earlier in this
session (task 359 + a post-hoc regression fix). Also checked consistency against the closely
related `HealthImpact.tsx`, since both components read the same symptom logs and the same
condition taxonomy — findings there are included only where they bear on that shared
boundary, not as a general HealthImpact audit.

## Error paths

Clean. `fetchSymptomLogs` failure sets `loadError` and renders a distinct "Couldn't load
your symptom history" card, checked ahead of the "not enough data" and loading states. No
gaps found.

## Loading / pending states

Clean. `loading` renders its own card before either the error or data-driven states can
render.

## Third-party-service-down handling

Partial gap, not in this feature's own fetch, but in a signal it consumes:

- **`current` (from `App.tsx`) can go stale with no signal.** `App.tsx`'s `loadData` only
  sets `current` on a *successful* fetch (`App.tsx:136`); on failure it sets `error` and
  leaves `current` at whatever it last was (`App.tsx:139-142`). `current` is never reset to
  `null`. Insights' `computeTodayRisk` treats a non-null `current` as *live, right now* data
  (`symptomAnalysis.ts:137-160`) with no timestamp or staleness check. The `"no-current-data"`
  status only fires before the very first successful load ever completes — once one fetch has
  succeeded, an outage on a later 5-minute poll leaves "Today's Symptom Risk" silently
  computing from a snapshot that could be hours old, with zero indication anywhere on that
  card that it isn't current. `App.tsx` never threads its `error` state into `Insights`/
  `TrendsModal` at all (only `current` is passed, at `TrendsModal.tsx:60` /
  `App.tsx:574-579`) — unlike `HealthImpact`/`CurrentConditions`, which do receive `error` as
  of task 362.

## Consistency across touchpoints

- **The condition-taxonomy mismatch (original review's B4/B5) is still fully present.**
  `SymptomLogger.tsx` persists the preset **label** string as a symptom log's tag
  (`tags: selectedTags`, `SymptomLogger.tsx:88`, using `CONDITION_LABELS`,
  `SymptomLogger.tsx:13-27`). `Insights.tsx`/`symptomAnalysis.ts` group and display by that
  same tag string, so **Insights itself is internally self-consistent and not affected**.
  But `HealthImpact.tsx`'s `getPersonalizedRiskInfo` looks up `conditionStats[risk.condition]`
  and `patterns[risk.condition]`, where `risk.condition` comes from a **third, independent**
  vocabulary defined in `healthLogic.ts`/`healthRisks.ts`. Comparing all 13 pairs:

  | key | SymptomLogger tag | risk.condition | match? |
  |---|---|---|---|
  | migraine | "Migraines" | "Migraine" | ✗ |
  | cluster | "Cluster Headache" | "Cluster Headache" | ✓ |
  | pots | "POTS / Dysautonomia" | "POTS / Dysautonomia" | ✓ |
  | mecfs | "ME/CFS" | "ME/CFS / PEM" | ✗ |
  | joints | "Joint Pain" | "Joint Pain (Arthritis)" | ✗ |
  | fibromyalgia | "Fibromyalgia" | "Fibromyalgia" | ✓ |
  | eds | "EDS" | "EDS / Hypermobility" | ✗ |
  | raynauds | "Raynaud's" | "Raynaud's" | ✓ |
  | sinus | "Sinus" | "Sinus / Sinusitis" | ✗ |
  | sleep | "Sleep Quality" | "Sleep Quality" | ✓ |
  | aqi | "Air Quality" | "Air Quality" | ✓ |
  | geomagnetic | "Geomagnetic" | "Geomagnetic Storm" | ✗ |
  | pollen | "Pollen" | "Pollen & Mold" | ✗ |

  **7 of 13 mismatch** — exactly the count the original architecture review's B5 predicted.
  `HealthImpact.tsx`'s "Your pattern: Nx logged" (`HealthImpact.tsx:152-159`) silently shows
  `0x logged` for all 7, even when the user has logged that exact condition dozens of times
  via the same modal that's supposed to feed this card. And `patterns[condition]`
  (`HealthImpact.tsx:418-426`) can only ever match Fibromyalgia — the other 3 keys
  (`Migraines`/`Sinus`/`ME/CFS`) never fire, for the same reason.

  **This is significant because lair task 360 ("unify the 13-condition list... causes 2
  silent bugs") was explicitly scoped this session to be the fix for B4/B5, but the work
  actually done only unified the `HEALTH_CONDITIONS` array used for Settings/Onboarding
  toggle ordering — it never changed `SymptomLogger` to persist `key` instead of `label`, and
  never touched `HealthImpact.tsx`'s lookup. Task 360 is marked `done` but its own stated
  goal (fixing the 2 silent bugs) is not actually complete.**

- **A fabricated, date-specific health claim is still live.** `HealthImpact.tsx:420`:
  `Migraines: kpIndex > 4 && humidity > 85 ? "This matches your May 16 pattern" : ""` — a
  literal hardcoded date presented as if it were a real personalized comparison. This is the
  same class of bug as B12 (fixed in `Insights.tsx` this session — the "What Helps Your
  Symptoms" hardcoded claims), but the near-identical bug in this sibling file was not caught
  or fixed. (It also can't ever render today regardless, per the table above — the key
  `"Migraines"` never matches `risk.condition` `"Migraine"`.)

- **Threshold drift between the two components for the same signal.** `symptomAnalysis.ts`'s
  canonical high-humidity trigger is `> 85` (`symptomAnalysis.ts:50`). `HealthImpact.tsx` uses
  `humidity > 90` for its "High Humidity" active-trigger chip (`HealthImpact.tsx:411`) *and*
  `humidity > 85` for the (non-functional) Migraines pattern check three lines later
  (`HealthImpact.tsx:420`) — two different literal thresholds for the same concept inside one
  function, neither matching Insights' canonical value. This corroborates the original
  review's own D5 finding ("Inline thresholds contradict the risk engine... three different
  definitions of 'elevated AQI' in one frontend") — already documented, still unfixed, and not
  part of any task this session touched.

- **`Insights.tsx`'s own "Dangerous Combinations" banner duplicates thresholds instead of
  reusing `symptomAnalysis.ts`.** `Insights.tsx:357-361` re-implements
  `humidity > 85`/`aqi > 45`/`kpIndex > 4` inline against raw `symptomLogs`, rather than
  calling the `matchesLog` predicates already exported (in spirit, if not literally exported)
  from `TRIGGER_FACTORS` in the very same module it just imported three functions from. A
  future change to any of these three thresholds in `symptomAnalysis.ts` would silently not
  propagate to this banner.

## Honesty check — what got cut

Task 359 explicitly targeted 5 numbered bugs (B3, B6, B12, B13, B16) plus an extraction to a
testable util — all 5 were fixed correctly and are now covered by tests. What that task did
**not** cover, and what wasn't caught until this review:

- B4 and B5 (condition-taxonomy mismatch) — pre-existing, catalogued, high-severity, and
  incorrectly believed closed by task 360.
- The identical fabricated-claim bug pattern (B12's class) recurring in `HealthImpact.tsx`.
- The inline-threshold-duplication finding (original review's D5) was known before this
  session and remains unaddressed.

None of this was silently dropped from task 359's own scope — it's scope that was never
assigned to any task, surfaced here because this review checked consistency at the Insights/
HealthImpact boundary rather than treating each file in isolation.

## Candidate learnings

- A prop treated as "live, right now" data downstream (e.g. `current`) needs either a
  staleness timestamp or the parent's error state threaded alongside it — otherwise a later
  fetch failure renders stale data as confidently current, with no distinguishing signal at
  the point of use.
